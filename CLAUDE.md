# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

Personal [ZMK](https://zmk.dev) firmware configuration for a custom "Corne Choc Pro" split keyboard (nRF52840-based, 3x6+3 columns per half). The keymap layout is inspired by [optimot](https://optimot.fr/) and adds extra layers for Greek letters and French accented characters. This is a ZMK **user config repo** (the `config/` self-module referenced by `config/west.yml`), not the ZMK firmware itself — firmware sources are pulled in at build time via west.

## Build

Firmware is built exclusively via GitHub Actions (`.github/workflows/build.yml`), which delegates to ZMK's reusable `build-user-config.yml` workflow. There is no local build tooling in this repo (no Makefile/script) — pushing to GitHub (or opening a PR) is how you get firmware binaries, produced as workflow artifacts.

- `build.yaml` defines the build matrix: which board + shield + snippet combos get built. Currently: `corne_choc_pro_left`/`corne_choc_pro_right` with the custom `nice_view_disp` display shield (see below) and `studio-rpc-usb-uart` snippet (for ZMK Studio support), plus a `settings_reset` variant of each half for clearing stored settings on the controller.
- `config/west.yml` is the west manifest: pins ZMK to `v0.3`, and pulls in two modules from `urob`: `zmk-unicode` (Unicode/dead-key input via `&uc`) and `zmk-helpers` (the `ZMK_BEHAVIOR(...)` macro sugar used throughout the keymap).
- There is no local test suite or linter — validate keymap changes by reading the devicetree carefully and letting the CI build catch syntax/compile errors, or by building locally with `west` if you have a Zephyr/ZMK toolchain set up (not present in this repo).

## Architecture

Two logically separate things live side by side and are easy to conflate:

1. **The board definition** (`boards/arm/corne_choc_pro/`) — the hardware description for this custom keyboard: pin/matrix transform (`corne_choc_pro.dtsi`), physical key layouts for a 6-column and a 5-column variant (`corne_choc_pro-layouts.dtsi`, with `default_layout`/`five_col_layout` physical-layout nodes and matching position maps), per-half `.dts`/`_defconfig` files for left/right, and Kconfig glue. It also contains its own `corne_choc_pro.keymap`, which is effectively a stale/reference copy — it is **not** what gets built.
2. **The active user keymap** (`config/corne_choc_pro.keymap`) — this is the file that actually defines behavior and is what you should edit when changing the layout. It's picked up via `board_root: .` in `build.yaml` + the `self.path: config` entry in `west.yml`. `config/corne_choc_pro.conf` holds Kconfig overrides (mouse emulation, sleep/idle timeouts, keyboard name — currently all commented out), and `config/corne_choc_pro.json` is the ZMK Studio / keymap-editor physical layout description.

### Keymap structure (`config/corne_choc_pro.keymap`)

- Six layers, each with an ASCII-art comment diagram above its `bindings` block showing the physical key grid — **keep these diagrams in sync when changing bindings**, they're the primary way to reason about the layout: `default_layer` (OPTIMOT French layout), `symbol_layer`, `greek_layer`, `navigation_layer`, `function_layer` (Bluetooth profiles + F-keys), `accent_layer` (precomposed circumflex/diaeresis letters plus combining marks, held from the Del thumb).
- Layers are accessed via `&lt N ...` (layer-tap) on the thumb keys (e.g. `&lt FUNCTION ESC`, `&lt ACCENT DEL`), not via a dedicated momentary-layer key — check existing `&lt`/`&mo` usage before adding a new layer-access binding. Layer indices are positional (order in the `keymap { }` node) and are referenced through the `#define DEFAULT 0` … `#define ACCENT 5` names at the top of the keymap, so inserting/removing a layer means updating those defines.
- Home row mods use two custom `hold-tap` behaviors, `hml` (left hand) and `hmr` (right hand), both `"balanced"` flavor with a 140ms tapping term and `hold-trigger-on-release`. The home row is fully symmetric: Gui/Alt/Ctrl/Shift on A/I/E/U (left) and N/R/S/T (right). Each declares `hold-trigger-key-positions` as the *opposite* hand's key positions (46-key numbering: rows 0–13, 14–27, 28–39, thumbs 40–45) — this is what prevents the home-row-mod hold from firing on same-hand rolls. If you change the physical key count/order (e.g. editing `corne_choc_pro-layouts.dtsi`), these position lists must be updated to match.
- Custom `mod_morph` behaviors (declared with the `ZMK_BEHAVIOR(...)` macro from `zmk-helpers`) implement "smart" punctuation keys that change output based on Shift/Alt: e.g. `COMMA_OPT` (comma / shift→semicolon), `QUOT_OPT` (quote, nests alt→backtick/doublequote under shift→underscore), `SLSH_OPT`, `DASH_OPT`. These follow a two-level nesting pattern (an alt-morph feeding into a shift-morph) — follow that pattern if adding new overloaded punctuation keys.
- French/Greek accented characters are emitted via `&uc UC_FR_*` / `&uc UC_EL_*` Unicode macros from the `zmk-unicode` module (see `keys-extra.h` for available glyph names), with `default-mode = UC_MODE_LINUX` set globally via `&uc { ... };`. Some accented letters are their own named `mod_morph` behaviors with an alt-modified variant: `c_ced` (c / alt→ç, on the base layer), `a_ae`/`e_oe` (a / alt→æ, e / alt→œ, tapped through the `hm_a`/`hm_e` home-row-mod hold-taps on the base layer, since A and E are also Gui/Ctrl) and the `*_hat` family (`a_hat`, `e_hat`, …: circumflex / alt→diaeresis, on the accent layer).
- `hm_upsilon`/`hm_tau` are one-off `hold_tap` behaviors combining a home-row mod (tap → key) with a Greek letter Unicode macro (hold → `&uc_upsilon`/`&uc_tau`), used only on the Greek layer.

### Display shield (`boards/shields/nice_view_disp/`)

A custom fork/variant of the community `nice_view` display shield with a custom status screen (`custom_status_screen.c`) and widgets (`widgets/*.c`: central status, peripheral status, shared utils such as `draw_battery`). Edit widget `.c`/`.h` files here to change what's shown on the screen; `nice_view_disp.overlay` and `.conf`/`Kconfig.*` wire it up as a shield selectable via `build.yaml`'s `shield:` field.

The left (central) half's status screen (`widgets/status.c`) is three 68×68 canvases drawn upright then rotated: the top one holds battery/output and the start of the active layer's icon; the layer icon (68×66: Optimot-style key grids for the base/Greek/symbol/accent layers, a compass rose and a gear) spills over into the middle canvas, which also holds a 2×2 grid of modifier tiles at its bottom (Gui/Alt/Ctrl/Shift, in home-row order, filled while held; the Shift tile also shows caps word as an outlined pill and caps lock as a filled one), and the bottom one (only its top 24 rows are on screen) the 5 Bluetooth profiles (bare number, a bar under paired ones, a filled pill for the active one), shown 5..1 from left to right to mirror the `&bt BT_SEL` keys on the function layer (keep the two in sync if either changes). Modifiers and caps state are polled every 50 ms by an `lv_timer`: ZMK v0.3 raises no usable event for them, and caps word is read from the behavior's private device data (`bool active`), so re-check that if the ZMK version changes. The icons are generated by `tools/gen_status_icons.py` into `widgets/status_icons.c`/`.h`, along with the tray icons shared by both halves (rounded battery frame, 2-bit charging bolt, Bluetooth connection icons; USB still uses the LVGL font symbol) in `widgets/tray_icons.c`/`.h` — edit the generator, not the generated files; layer icons are indexed by layer position in the keymap, so update `LAYERS` there when adding, removing or reordering layers. Caps lock comes from HID indicators (`ZMK_HID_INDICATORS`, selected in `Kconfig.defconfig` for the central).

The right (peripheral) half shows a pixel-art moon cycling through its phases (one cycle per hour, one step per minute, driven by an `lv_timer` in `widgets/peripheral_status.c`). The full-moon base image (texture, stars, "AntiCorne" label) is generated by `tools/gen_moon.py` into `widgets/moon_bitmap.h` — regenerate it rather than editing the header; `widgets/moon.c` computes the tilted phase shadow at runtime and writes the 1-bit LVGL image, rotated 90° because the screen is mounted sideways (the art is designed upright at 68×140, stored as 140×68). Note the nice!view shows LVGL *white* as a dark pixel (the default `LVGL_BACKGROUND` is `lv_color_white()` and appears black), so image palettes are polarity-flipped relative to what you'd expect.
